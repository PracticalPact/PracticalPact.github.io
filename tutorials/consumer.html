Consumer tutorial

This tutorial will teach you to implement Consumer-Driven Contract Testing (CDCT) for a Consumer. If you do not know what CDCT or a Consumer is, read this short introduction before you continue.

To set up a given microservice as a Consumer, the following steps are followed.

Running Example

During this tutorial, a running example will be used for code snippets. It is a very simple frontend for a forum where you can create posts. If you wish, you can explore it on GitHub. The main branch has the full code including the Consumer tests.

Consumer contract sequence diagram

In CDCT, the Consumer defines the API interactions it depends on by creating contract tests. These tests describe the requests the Consumer sends and the responses it expects from the Provider. The generated contracts are published to the Pact Broker, where they can be verified by Providers. This ensures that service integrations remain compatible as systems evolve. This is done by sending requests to a mock provider and verifying that the Consumer behaves as expected. You can see this visualised in the sequence diagram below. You do not need to fully understand it now, but may find it useful to refer back to later.

Create Test File

See below for test file examples for both C# and JavaScript.

Create a new project, which you can call ConsumerTests. The C# example below uses xUnit, but Pact can be used with other test frameworks as well.

Install the nuget packages PactNet version 5.0.1. If you use Xunit, also install PactNet.Output.Xunit version 1.0.0. The following is an example of what might be in the project file.

    <ItemGroup>
        <PackageReference Include="Microsoft.NET.Test.Sdk" Version="17.14.1" />
        <PackageReference Include="PactNet" Version="5.0.1" />
        <PackageReference Include="PactNet.Output.Xunit" Version="1.0.0" />
        <PackageReference Include="xunit" Version="2.9.3" />
        <PackageReference Include="xunit.runner.visualstudio" Version="2.5.4" />
    </ItemGroup>

  <ItemGroup>
    <Using Include="Xunit" />
  </ItemGroup>

Create a new class to carry out the tests. Consider calling it ConsumerTests.cs. Paste in the following code and replace [TEST_CLASS_NAME] with your chosen class name. Replace [PROVIDER NAME] with the name of the Provider that you are writing tests for. Make sure it matches its repository name to avoid confusion. Finally, replace [CONSUMER NAME] with the name of your current microservice. This is simply a fallback value when running locally; on the CI pipeline, it will be replaced by your repository name. 

using System.Net;
using PactNet;
using PactNet.Matchers;
using PactNet.Output.Xunit;
using Xunit.Abstractions;

public class [TEST_CLASS_NAME]
{
    private readonly IPactBuilderV4 _pact;

    public [TEST_CLASS_NAME](ITestOutputHelper output)
    {
        var config = new PactConfig
        {
            Outputters = [new XunitOutput(output)],
            PactDir = Path.Combine("..", "..", "..", "..", "pacts")
        };

        _pact = Pact.V4(Environment.GetEnvironmentVariable("REPOSITORY_NAME") ?? "[CONSUMER NAME]", "[PROVIDER NAME]", config).WithHttpInteractions();
    }
}

You have now created the boilerplate setup, which defines who the Consumer and who the Provider is. It also specifies where the contracts will be placed locally (in your repository root) and how logging works. In the next section you'll be able to see the running example version of this setup.

Create Scenarios

Now it is time to create the Scenarios of the Contract. If you are uncertain about what a Scenario is or how a Contract is structured, read this short explanation before you continue.

For each Scenario, we need to specify what the request will be, and what the rules for the response are. Remember that this also includes an example of a response that follows those rules. We of course also need to make a description of the Scenario and define a Provider State.

Additionally, we also need to prove that our Consumer actually is capable of sending the requests that we specify, and that it can handle a response that follows the rules we laid out. This is a safety check to ensure that we do not make a Contract that we ourselves can't obey.

The Pact framework helps us here. It has functionality to spin up a mock HTTP server that we can send real HTTP requests to. For each Scenario we describe, it will expect us to send it an HTTP request that is identical to what we described in the Scenario. It will then respond according to the example response we provided in the Scenario. This way, each Scenario will be executed as a test. If all tests pass, the Scenarios will be combined into a final Contract.

When performing these tests, it is crucial that the code we use to send the requests is the same as the production code. Otherwise we might get a disconnect between the real behaviour and what we are testing. This would be troublesome, if we later on changed the production code without remembering the test code.

Each Scenario is written in its own test method and consists of two parts. The first part is the Scenario, and the second part is the test. The following is a rough template for what it can look like. A bit further down you can see an example of what it would look like for our running example.

[Fact]
public async Task [TEST_NAME]()
{
    // Scenario:
    _pact
        .UponReceiving("[DESCRIPTION OF REQUEST]")
        .Given("[PROVIDER STATE]")
        .WithRequest([HTTP METHOD], "[ENDPOINT]")
        .WithHeader("[HEADER NAME]", "[HEADER VALUE]")
        .WillRespond()
        .WithStatus([STATUS CODE])
        .WithJsonBody(new
        {
            [RESPONSE_FIELD] = Match.MinType(new
            {
                id = Match.Type("[EXAMPLE ID]"),
                value = Match.Type("[EXAMPLE VALUE]")
            }, 1)
        });

    // Test:
    await _pact.VerifyAsync(async ctx =>
    {
        var client = new HttpClient { BaseAddress = ctx.MockServerUri };

        var request = new HttpRequestMessage([HTTP METHOD], "[ENDPOINT]");
        request.Headers.Add("[HEADER NAME]", "[HEADER VALUE]");

        var response = await client.SendAsync(request);

        Assert.Equal([STATUS CODE], response.StatusCode);
    });
}

Running Example

Below is the entire consumer test code for the running example. It has three Scenarios: a successful get, a failed get, and a successful post. There are of course more possible Scenarios, but this is enough for now.

using System.Net;
using PactNet;
using PactNet.Matchers;
using PactNet.Output.Xunit;
using Xunit.Abstractions;
using ForumFrontend;

namespace ConsumerTests;

/// <summary>
/// This performs Consumer tests for the Provider called example-provider-csharp and creates the Contract.
/// </summary>
public class ExampleProviderCsharpTest
{
    private readonly IPactBuilderV4 _pact;

    public ExampleProviderCsharpTest(ITestOutputHelper output)
    {
        var config = new PactConfig
        {
            Outputters = [new XunitOutput(output)],
            PactDir = Path.Combine("..", "..", "..", "..", "pacts")
        };

        _pact = Pact.V4(Environment.GetEnvironmentVariable("REPOSITORY_NAME") ?? "example-consumer-csharp", "example-provider-csharp", config).WithHttpInteractions();

    }

    [Fact]
    public async Task GetAllPosts_IsLoggedIn_ReturnsAllIds()
    {
        string sessionId = "valid-token";

        _pact
            .UponReceiving("a request for all posts with a valid session id")
            .Given($"a user with at least one post is logged in with session id: {sessionId}")
            .WithRequest(HttpMethod.Get, "/posts")
            .WithHeader("session-id", sessionId)
            .WillRespond()
            .WithStatus(HttpStatusCode.OK)
            // This specifies the response body. It must have a field called posts.
            // MinType means that it must be an array of a particular type with length of at least 1.
            // post-id-1 is an example entry, which we can then check for below. It also lets the type matcher infer that posts needs to be an array of strings.
            .WithJsonBody(new
            {
                posts = Match.MinType("post-id-1", 1)
            });

        await _pact.VerifyAsync(async ctx =>
        {
            using PostClient postClient = new(ctx.MockServerUri);
            var result = await postClient.GetAllPosts(sessionId);

            var sucResult = Assert.IsType<SuccessResult<PostClient.GetAllPostsResponse>>(result);
            Assert.NotNull(sucResult.content);
            Assert.Equal(["post-id-1"], sucResult.content.Posts);
        });
    }

    [Fact]
    public async Task GetAllPosts_IsNotLoggedIn_GivesUnauthorizedError()
    {
        string sessionId = "invalid-token";

        _pact
            .UponReceiving("a request for all posts with invalid session id")
            .Given($"no user exists with session id: {sessionId}")
            .WithRequest(HttpMethod.Get, "/posts")
            .WithHeader("session-id", sessionId)
            .WillRespond()
            .WithStatus(HttpStatusCode.Unauthorized);

        await _pact.VerifyAsync(async ctx =>
        {
            using PostClient postClient = new(ctx.MockServerUri);
            var result = await postClient.GetAllPosts(sessionId);

            Assert.IsType<UnauthorizedErrorResult>(result);
        });
    }

    [Fact]
    public async Task CreateNewPost_IsLoggedIn_ReturnsNewId()
    {
        string sessionId = "valid-token";
        string title = "A Post Title";
        string content = "Post content";

        _pact
            .UponReceiving("a request to create a new post")
            .Given($"a user is logged in with session id: {sessionId}")
            .WithRequest(HttpMethod.Post, "/posts")
            .WithHeader("session-id", sessionId)
            .WithJsonBody(new{
                title = title,
                content = content
            })
            .WillRespond()
            .WithStatus(HttpStatusCode.Created)
            // This specifies the response body. It must have a field called id of type string.
            .WithJsonBody(new
            {
                id = Match.Type("new-post-id")
            });

        await _pact.VerifyAsync(async ctx =>
        {
            using PostClient postClient = new(ctx.MockServerUri);
            var result = await postClient.CreateNewPost(sessionId, title, content);

            var sucResult = Assert.IsType<SuccessResult<PostClient.CreateNewPostResponse>>(result);
            Assert.NotNull(sucResult.content);
            Assert.Equal("new-post-id", sucResult.content.Id);
        });
    }
}

All together an example of GET ALL FAVORITES is shown below:

/** @jest-environment node */

const FavoritesClient = require("../favoritesClient");  // Client used to call Favorite

const path = require("path");
const axios = require("axios");

// Pact + matchers for defining expected interactions and responses
const { Pact, Matchers } = require("@pact-foundation/pact");
const { eachLike, like } = Matchers;

// Contract tests between frontend (consumer) and Favorites API (provider)
describe('Favorites API Pact', () => {

    // Pact mock server setup
    const pact = new Pact({
        consumer: process.env.REPOSITORY_NAME,
        provider: 'ds-favorite-clone--oliverndmagnus',
        dir: path.resolve(process.cwd(), "pacts"),
        logLevel: 'info',
        pactfileWriteMode: "overwrite",
    });

    // One test scenario: successful GET
    it('gets all favorites for a user', async () => {

        await pact
            .addInteraction()

            // Preconditions for the provider state
            .given('a player with session token aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa exists with favorites and highlights')

            // Description of request
            .uponReceiving('a request for all favorites with that token')

            // Expected request from the consumer
            .withRequest('GET', '/v1/casino/game', (builder) => {
                builder
                    .headers({ 'x-session': 'aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa' });
            })

            // Expected response
            .willRespondWith(200, (builder) => {
                builder.jsonBody({
                    favorites: eachLike({
                        id: like("c42dcc42-281d-f111-8f81-005056875d96"),
                        entityId: like("ddff3a8fd1234c58821c1e00e4fbedc6"),
                        creationDate: like("2026-03-11T08:56:59+00:00"),
                        updatedDate: like("2026-03-11T14:39:53+00:00")
                    }),
                    highLights: eachLike({
                        id: like("c42dcc42-281d-f111-8f80-005056875d96"),
                        entityId: like("ddff3a8fd1234c58821c1e00e4fbedc6"),
                        creationDate: like("2026-03-11T08:56:59+00:00"),
                        updatedDate: like("2026-03-11T14:39:53+00:00")
                    })
                });
            })

            // Send the request to the mock server and evaluate its response
            .executeTest(async (mockServer) => {
            const client = new FavoritesClient(mockServer.url);
            const response = await client.get("aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa");

            // Validate structure of response
                expect(response.status).toBe(200);
                expect(Array.isArray(response.data.favorites)).toBe(true);
                expect(Array.isArray(response.data.highLights)).toBe(true);
            });
    });
});
  1. It sets up Pact between CasinoFrontend and FavoriteAPI
  2. It defines one expected GET request for favorites
  3. It defines the response the mock provider should return
  4. It sends the request to Pact's mock provider
  5. It checks that the response status is 200
  6. Pact saves the interaction as a contract in the pacts folder

If you have multiple Providers, you should make a separate file for each, as they will get their own Contracts.

Do not place any sensitive information in your Contracts.

Continuous Integration (CI)

You have now created the Contracts locally. However, for the Provider to make use of it, it must be uploaded to the Broker. This is done in the CI pipeline. Therefore you must add a CI script. These examples use GitHub Actions.

First go to your repository settings and add a variable called BROKER_URL. Set it to your broker url.

Next create a file in .github/workflows/ called ci.yml . Look in the examples below to find the specific contents. 

name: CI

on: [push]

env:
    REPOSITORY_NAME: ${{ github.event.repository.name }}

jobs:
  generate-pacts:
    name: Run Contract Tests
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6

      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: "npm"
          cache-dependency-path: package-lock.json

      - name: Install dependencies
        run: npm ci

      - name: Run pact tests
        run: npm run test:pact

      - name: Publish pacts
        run: npx pact broker publish pacts --consumer-app-version ${{ github.sha }} --broker-base-url ${{ vars.BROKER_URL }} --branch ${{ github.ref_name }}

      - name: Register repository URL
        shell: pwsh
        run: | 
          Invoke-RestMethod `
          -Method Patch `
          -Uri "${{ vars.BROKER_URL }}pacticipants/${{ env.REPOSITORY_NAME }}" `
          -ContentType "application/merge-patch+json" `
          -Body '{"repositoryUrl": "https://github.com/${{ github.repository }}", "mainBranch": "main"}'

      - name: Register version
        shell: pwsh
        run: |
          Invoke-RestMethod `
            -Method Put `
            -Uri "${{ vars.BROKER_URL }}pacticipants/${{ env.REPOSITORY_NAME }}/versions/${{ github.sha }}" `
            -ContentType "application/json" `
            -Body '{"branch": "${{ github.ref_name }}"}'

name: CI

on: 
  push

env:
  GITHUB_PACKAGE_USER_NAME: ${{ github.actor }} 
  GITHUB_PACKAGE_TOKEN: ${{ secrets.GITHUB_TOKEN }}
  GIT_BRANCH: ${{ github.ref_name }}
  GIT_SHA: ${{ github.sha }}
  REPOSITORY_NAME: ${{ github.event.repository.name }}

jobs:
  build-service:
    name: Build and Test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5

      - name: Setup .NET Core SDK
        uses: actions/setup-dotnet@v5
        with:
          dotnet-version: "10.0.x"

      - run: dotnet restore
      - name: Build
        run: dotnet build --no-restore
      - name: Run normal tests 
        run: dotnet test --no-build --filter "Category!=Contract"
      - name: Run consumer contract tests
        run: dotnet test --no-build --filter "Category=Contract&ContractRole=Consumer"

      - name: Register repository URL
        shell: pwsh
        run: | 
          Invoke-RestMethod `
          -Method Patch `
          -Uri "${{ vars.BROKER_URL }}pacticipants/${{ env.REPOSITORY_NAME }}" `
          -ContentType "application/merge-patch+json" `
          -Body '{"repositoryUrl": "https://github.com/${{ github.repository }}", "mainBranch": "main"}'

      - name: Publish Pacts
        uses: PracticalPact/pactbroker-webhook-action/publish-pacts-action@main
        with:
          brokerUrl: ${{ vars.BROKER_URL }}
          consumerVersion: ${{ github.sha }}
          branch: ${{ github.ref_name }}

      - name: Run provider contract tests
        run: dotnet test --no-build --filter "Category=Contract&ContractRole=Provider"

After pushing, you should be able to see your Contract in the Broker.

Continuous Deployment (CD)

Finally, we will add CD to the pipeline. Before we deploy our microservice anywhere, we want to make sure that our Providers are correctly deployed.

Make a new file called cd.yml in .github/workflows with the contents. It will first check if our Providers are correctly deployed, and then record our deployment. This example is in GitHub Actions and does not actually perform a deployment; it simply marks it in the Broker for the purposes of CDCT.

While the CI script from before is run automatically, this must be triggered manually from the Actions page. This is only possible once it has been merged into main, so you may not be able to do it for a while.

name: CD
run-name: CD - ${{ inputs.environment }}

on:
  workflow_dispatch:
    inputs:
      environment:
        type: choice
        options:
          - town21
          - town24
          - production
env:
  REPOSITORY_NAME: ${{ github.event.repository.name }}

jobs:
  can-i-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: PracticalPact/pactbroker-webhook-action/can-i-deploy-consumer-action@main
        name: Can I Deploy?
        with:
          brokerUrl: ${{ vars.BROKER_URL }}
          brokerToken: ${{ secrets.PACT_BROKER_TOKEN }}
          consumerName: ${{ env.REPOSITORY_NAME }}
          consumerVersion: ${{ github.sha }}
          toEnvironment: ${{ inputs.environment }}
          retryWhileUnknown: 10
          retryInterval: 15

  deploy:
    needs: can-i-deploy  
    runs-on: ubuntu-latest
    steps:
      - name: Deploy
        run: echo "Deploying to ${{ inputs.environment }}..."
      - name: Record Deployment
        uses: PracticalPact/pactbroker-webhook-action/record-deployment-action@main
        with:
          brokerUrl: ${{ vars.BROKER_URL }}
          applicationName: ${{ env.REPOSITORY_NAME }}
          version: ${{ github.sha }}
          environment: ${{ inputs.environment }}
