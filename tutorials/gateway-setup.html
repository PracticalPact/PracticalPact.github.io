Setting Up Gateway Testing

Setting a gateway up for CDCT testing is a one-time process. Once it has been done, the gateway will be able to automatically transform contracts according to its own behaviour. The idea is that the gateway will run while verifying a contract that targets it as a provider. As it does, it will observe how each request is transformed when it goes through the gateway. These transformed requests are then turned into a new contract where the gateway is the provider. Follow the instructions on this page to set up the gateway testing. Currently only C# is supported.

Create Test Setup

Create the files required to run the provider tests.

Perform the following steps.

New Project

In the solution, create a new project. This project will contain all Provider tests for the solution. If you have no other naming conventions established, consider calling it ContractTests. Choose a test framework such as xUnit or MSTest and set up the test project as you normally would.

If instead your organisation prefers to have all tests within a single project, make a directory in that project called ContractTests.

Packages

In the test project, install the nuget packages PracticalPact.Gateway and PracticalPact.Utilities.

Main file

Create GatewayContractTests.cs with the following contents. Make necessary adjustments if you do not use xUnit. Also set [GATEWAY_NAME] to the name of the github repository of the gateway.

using PracticalPact.Gateway;
using PracticalPact.Utilities;
using PactNet;
using PactNet.Infrastructure.Outputters;
using PactNet.Output.Xunit;
using PactNet.Verifier;
using Xunit.Abstractions;

namespace ContractTests;

public class GatewayContractTests(ITestOutputHelper output)
{
    [Fact]
                public async Task ContractTest()
    {
                // --- Start server ----
                var app = Program.Create([], builder =>
            {
                builder.Services.AddGatewayTestingServicesWithYarp();  // Must be changed if Gateway does not use YARP.
            });
        app.UseGatewayTesting();
                await app.StartAsync();

                // --- Configuration (sets log output location) ---
                var config = new PactVerifierConfig
        {
            Outputters = new List<IOutput>
            {
                new XunitOutput(output)
            }
        };

                // --- Configure how to fetch and publish contracts ---
        EnvVerifierSourceFactory sourceFactory = new("[GATEWAY_NAME]", "http://localhost:9292/");
        sourceFactory.SetPublishFromLocalFallback();  // For intial testing; remove once setup is done

                // --- Run tests ---
        GatewaySetupUtility.VerifyGateway(
            sourceFactory.GetApplicationName(), 
            config, 
            app, 
            sourceFactory.ProduceVerifierSource);
    }
}

Start App

In the code template above, it is assumed that the app can be built with Program.Create, and that it lets you pass a delegate to modify the builder. Modify it to fit your setup. If you are not able to start the app like that, the next section will help you make the correct refactoring.

AddGatewayTestingServices

In order for the gateway testing to work, any HTTP client used by the gateway needs to make use of CatchTransformedResponseHandler in the PracticalPact.Gateway.Execution namespace. How this is done depends on how your Gateway is built.

  • YARP
    The code snippet above assumes you use YARP, and the Handler is added with AddGatewayTestingServicesWithYarp. No changes are needed.
  • Most other solutions
    In most cases, calling AddGatewayTestingServicesWithFilter instead will work. It sets up a HttpMessageHandlerBuilderFilter. This will for example work if you have a custom built gateway that creates HttpClients with a HttpClientFactory.
  • Otherwise
    If the above fails, you need create your own way of adding the Handler. Calling AddGatewayTestingServices instead will give you a starting point, as it injects the handler as a transient service. Then it is up to you to use it.

Refactor

In the previous section, we saw that we need to be able to start the gateway from the test code and configure the builder. Normally, it is started through the main file and then just runs.

There are multiple ways to achieve this. It might be the case that your project already is correctly configured, in which case you can skip this section.

Consult the language specific instructions for help.

Besides being able to start the app from the test code, you need access to its builder, so you can inject services later. You also need access to the app before it is started so you can create new endpoints and set up test-specific middleware.

Microsoft recommends Microsoft.AspNetCore.Mvc.Testing for testing like this, but it does unfortunately not work with Pact.

Consider the options below for which applies to your solution. You may need to consult multiple of them to get everything to work.

Modern setup with all code in Program.cs

Most APIs have all the startup code in Program.cs. If your solution is set up like that, your Program.cs will look like the following.

using ...;

var builder = WebApplication.CreateBuilder(args);
// Set up builder...
var app = builder.Build();
// Set up app...

app.Run();

public partial class Program { }

If there is no Program class definition there, make one.

Rewrite Program.cs to look like the following.

using ...;

var app = CreateApp(args);
app.Run();

public partial class Program {
                public static WebApplication CreateApp(string[] args, Action<WebApplicationBuilder>? configureBuilder = null){
                var builder = WebApplication.CreateBuilder(args);
                // Set up builder...
    configureBuilder?.Invoke(builder);
                var app = builder.Build();
                // Set up app...

                return app;
  }
}

With this refactor, we will in the next section be able to start the app like this:

var app = Program.CreateApp([], builder => {
                // Modify builder...
});
// Modify app...

await app.StartAsync();

CI

Create a file called .github/workflows/ci.yml with the following contents.

name: CI

on: 
  push:
    branches:
      - 'main'
      - 'feature/**'
      - 'my-change'

env:
  GITHUB_PACKAGE_USER_NAME: ${{ github.actor }} 
  GITHUB_PACKAGE_TOKEN: ${{ secrets.GITHUB_TOKEN }}
  GIT_BRANCH: ${{ github.ref_name }}
  GIT_SHA: ${{ github.sha }}
  IS_CI: true

jobs:
  build-service:
    name: Build and Test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6

      - run: dotnet restore
      - name: Build
        run: dotnet build --no-restore
      - name: Run all tests 
        run: dotnet test

What Now?

Whenever you run the tests, it should take all the contracts targeting the gateway and turn them into new contracts. You can try to publish a contract where the provider’s name is written with the format [GATEWAY]---[PROVIDER]. For example my-gateway---my-backend. If, in that example, the Consumer was called my-frontend, then when you run the gateway tests, it should create a new contract with a Consumer called my-frontend---my-gateway and a Provider called my-backend.
