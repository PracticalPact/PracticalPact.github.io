How to set up infrastructure for our method

Overview

This guide describes the infrastructure requirements to deploy and run the system.
The system consists of two microservices:

  • Pact Broker — stores and manages Pact contracts, backed by a relational database. Deployed using a pre-built Docker image.
  • OAS Service — a .NET microservice that compares a Pact contract against an OpenAPI Specification (e.g. swagger.json) to validate syntax compatibility. Built from source and deployed as a container.

Requirements

1. Container Orchestration Platform

You need a platform capable of running and managing containers, such as Kubernetes or any Kubernetes-compatible alternative (e.g. Docker Desktop with Kubernetes, k3s, OpenShift).

The platform must be able to:

  • Pull and run Docker images
  • Build and run containerised .NET applications
  • Allow services to communicate with each other over an internal network

2. .NET SDK

The OAS Service is built from source. You need the .NET SDK installed to build and publish it. Check the repository for the specific version required.

3. Database

Pact Broker requires a relational database (e.g. MariaDB, MySQL, or PostgreSQL). You can run it as a container alongside the services or use a managed database service. Either way, it must be reachable from the Pact Broker container at startup.

The database requires persistent storage — do not use container-local storage, as data will be lost on restart.

Database credentials must be available to the Pact Broker container at runtime. These should not be hardcoded — use a secrets management solution appropriate for your platform (e.g. Kubernetes Secrets, a vault service, or a config server).

4. Networking

The services must be able to reach each other over the internal network:

  • OAS Service → Pact Broker: OAS Service fetches contracts from Pact Broker and must be able to resolve its hostname and reach its HTTP port.
  • Pact Broker → Database: Pact Broker must be able to reach the database on its configured port.
  • OAS Service → Internal services: OAS Service needs to fetch OpenAPI specifications (e.g. swagger.json) from other teams' services. These services are typically only accessible from within the company's internal network, so the OAS Service must be deployed inside the same internal cluster to reach them.

5. GitHub Token

The system will eventually notify provider repositories automatically when a contract verification fails — for example, by opening a pull request from your CI/CD pipeline to the affected repository.
For this to work, your CI/CD pipeline needs a GitHub token with permission to create pull requests on other repositories in your organisation.

How you provide this token depends on your CI/CD setup. One option is to use a self-hosted GitHub Actions runner with the token configured as a secret.

Deployment

Production

Production deployment depends on your container orchestration platform and CI/CD setup. The order matters due to dependencies:

  1. Database first — the database must be running and reachable before Pact Broker starts.
  2. Pact Broker second — must be running and reachable before OAS Service starts.
  3. OAS Service last — requires Pact Broker to be available on startup.

For each service, ensure environment variables are configured as described in the Environment Variables section below, and that credentials are injected securely from your secrets management solution.

Environment Variables

Pact Broker:

Variable Description
PACT_BROKER_DATABASE_ADAPTER Database adapter — e.g. mysql2 for MariaDB/MySQL, postgres for PostgreSQL
PACT_BROKER_DATABASE_HOST Database hostname
PACT_BROKER_DATABASE_PORT Database port (3306 for MySQL, 5432 for PostgreSQL)
PACT_BROKER_DATABASE_NAME Database name
PACT_BROKER_DATABASE_USERNAME Database user — should be injected from a secrets store at runtime
PACT_BROKER_DATABASE_PASSWORD Database password — should be injected from a secrets store at runtime

OAS-service:

Variable Description
PACT_BROKER_URL Internal URL of the Pact Broker (e.g. http://pact-broker:9292)

Refer to each service's repository for the full list of supported variables.
